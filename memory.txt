lunarHope GitHub Pages — Project Memory
=========================================

Last updated: 2026-10-16

## What this project is
A personal GitHub Pages site built with plain HTML, Tailwind CSS (CDN), and vanilla JavaScript.
It has a dark "space" theme with an optional light mode.

## Directory layout
- Root HTML entries stay at the repo root (GitHub Pages serves the root; relative
  links + file:// depend on it): index / explore / publish / view / find / jump / lobby.
- assets/             — shared site assets
    - theme.css, theme-toggle.js        (theme system)
    - local-data.js  (GENERATED), local-loaders.js  (hand-maintained)
- scripts/            — build/tooling
    - generate_local_data.py            (regenerates assets/local-data.js)
- Content dirs: blog/ (posts + legacy reader), tools/ (web tools), fire/ (game),
  resources/ (downloadables), data/ (JSON metadata).

## Key pages
- index.html         — Home / landing page
- explore.html       — Unified content hub (posts + tools + resources)
- publish.html       — Creator Studio (write/publish posts and tools)
- view.html          — Reader / tool launcher (view.html?type=post|tool&app=<file>);
                       sole tool launcher now that tools/use.html is gone
- blog/index.html    — Redirects to explore.html#posts (legacy)
- tools/index.html   — Redirects to explore.html#tools (legacy)
- find.html          — Bluetooth school uniform distance tool
- jump.html          — "Jump Jump" game
- lobby.html         — Online lobby: public room search + P2P chat (see "Multiplayer lobby" below)

## Vocabulary (UI labels — keep these consistent)
- Post / Posts     — blog content. Retired words: "Blog", "Blog post", "Article"
- Tool / Tools
- Resource / Resources
- Explore          — the content hub page (explore.html); tabs are All / Posts / Tools / Resources
- Creator Studio   — publish.html (its two type tabs are "Post" and "Tool")
- Back link label  — always "Back to Explore", whether you came from a post or a tool
- index.html's Cmd+K spotlight entries mirror the Explore tabs: All, Posts, Tools
- Routes and file names were NOT renamed: /blog/ and /tools/ still redirect, and
  blog/read.html?slug= still works as a legacy reader. Only visible labels changed.


## Data files (data/*.json)
- data/posts.json        — Post metadata, GENERATED from blog/posts/*.md frontmatter
  - Field order: title, author?, date?, tags, excerpt?, slug, url
    (same shape publish.html writes, so the two writers cannot drift)
  - url is always view.html?type=post&slug=<slug>
  - excerpt = first prose paragraph of the .md body, capped at 150 chars;
    explore.html shows it as the card description
  - Written by .github/scripts/generate-posts.js — never edit it by hand
- data/tools.json        — Web tool metadata, one entry per file in tools/
  - Fixed 8-field schema, in this order in every entry:
      name, desc, author, url, emoji, status, lang, langColor
  - Shared defaults: author "lunarHope", status "Live", lang "HTML", langColor "#e34c26"
  - desc must say what the code really does — never a promise the implementation
    does not keep; emoji is a real emoji, never a bare letter; url must resolve
    to a file directly inside tools/
  - Live tools: ke-biao.html, zhan-shu.html, sao-lei.html, c-u-t.html,
    calculator.html, todo.html, snake.html, tomato.html
  - tools/weather.html (hardcoded demo stub; its "global forecast" desc was never
    implemented) and tools/use.html (superseded by view.html) were deleted
  - The tactical shooter was renamed "po- -men- -er- -ru- -h-t-m-l.html" -> zhan-shu.html
- data/resources.json    — Downloadable resources metadata
- data/drafts.json       — Draft posts/tools

## Resources module
- resources/ folder contains downloadable files
- data/resources.json lists them (name, desc, file, size, type, date, tags)
- explore.html renders them as download cards
- When adding new resources:
  1. Put the file under resources/
  2. Add an entry in data/resources.json
  3. Run `python scripts/generate_local_data.py` to refresh assets/local-data.js

## Theme system
- assets/theme.css          — Light-mode overrides
- assets/theme-toggle.js    — Theme toggle (dark/light), stored in localStorage
- Every page includes assets/theme.css + assets/theme-toggle.js — EXCEPT tools/*.html, see below
- Default follows system preference, manual choice is remembered


## Tools (tools/*.html)
- Dark-only. They include neither assets/theme.css, assets/theme-toggle.js nor assets/local-data.js
  (nothing in tools/ calls loadLocalData, so the ~28 KB snapshot was dead weight).
- Why no theme: a tool runs inside view.html's iframe, so assets/theme-toggle.js would append
  its own floating toggle to the iframe and theme its own <html> independently of the
  parent page. assets/theme.css also overrides 199 selectors but skips opacity variants
  (bg-glow-green/20, border-glow-blue/50, hover:bg-glow-pink/30 ...), so a tool in
  light mode rendered half-converted. The parent page owns the theme.
- A back link inside a tool MUST use target="_top": without it the iframe navigates to
  explore.html, which lists tools, which open view.html, which opens another iframe —
  infinite nesting.
- Otherwise self-contained: each file keeps its own <style> and inline <script>. The four
  small tools (c-u-t, calculator, todo, tomato) use the Tailwind CDN plus the shared
  tailwind.config block (space-* / glow-* tokens), with no hardcoded hex outside it.

## Design system (shared visual language)
- index.html is the reference style; explore.html and publish.html mirror it
- Shared classes each page defines in its own <style>:
  - .spotlight-card — hover-follow radial highlight (needs the mousemove --mouse-x/--mouse-y JS)
  - .text-gradient / .text-gradient-glow
  - .reveal — scroll-in animation (IntersectionObserver adds .active)
  - .tab-btn — pill tab (explore.html holds the original definition)
- Shared layout: fixed blurred header, max-w-7xl container, floating glow blobs
  (bg-glow-purple/20 + bg-glow-blue/20 with blur-[120px] + animate-float) and the 24px grid
- Icons are inline stroke SVGs (Heroicons outline). Emoji are data only (tool emoji field)
  or brand glyphs (footer heart, theme toggle, terminal arrow)
- publish.html additionally defines .seg-btn (segmented control), .draft-card and .spinner
- publish.html .reveal uses an .armed state: an element is hidden only after JS arms it,
  so content stays visible if the script never runs

## Local file:// support
- Two files, on purpose (both in assets/):
    - assets/local-data.js      — GENERATED. A single global, `window.__localStore`, holding
      data/*.json only. Never hand-edit. ~22 KB at 37 posts.
    - assets/local-loaders.js   — HAND-MAINTAINED, ~2 KB. Defines __normalizeLocalKey,
      window.loadLocalData and window.loadLocalText.
- Pages include ONLY what they use:
    - reads the store (index, explore, publish, view): both scripts, loaders first
    - calls loadLocalText only (blog/read.html): local-loaders.js alone — that is why
      read.html loads ~14 KB of local JS instead of ~36 KB
    - calls nothing (find, jump, every page in tools/): neither script
- Splitting them is what keeps the ~22 KB index off pages that never read it.
  loadLocalData looks window.__localStore up at call time, so a page missing the store
  script just falls through to fetch().
- Post bodies (blog/posts/*.md) are always fetched, so reading a post needs a local
  server even for file://: `python -m http.server 8000`. view.html and blog/read.html
  show an "Offline" panel with that command instead of a misleading 404.
- Rationale: embedding every post body pushed local-data.js to ~214 KB at 37 posts,
  and that file is loaded by every page on the site.
- window.loadLocalData reads JSON from the embedded store under file://;
  window.loadLocalText is a plain fetch with no local store to look up.
- Both loaders work over http:// and file://; only the store lookup is file://-specific
- The GitHub Actions workflow runs this script too and commits local-data.js, so
  published content shows up offline as well; local-only edits still need a manual run
- Regenerate local-data.js after changing any data/*.json file:
  `python scripts/generate_local_data.py`
- For full dynamic behavior (GitHub API publish/delete), a local server is still recommended:
  `python -m http.server 8000`

## Unified Explore page (explore.html)
- Merges Posts + Tools + Resources into one page
- Features:
  - Type filter: All / Posts / Tools / Resources
  - Tag filter chips
  - Search by title/description/tag
  - Sort newest / A-Z
  - Push/update mechanism: detects new content since last visit and shows a banner

## Path conventions
- Use relative links (no leading "/") so file:// works
- Root pages: `explore.html`, `tools/index.html`, etc.
- Subdirectory pages: prefix `../` when linking to root files
- GitHub API paths (ghFetch('/contents/...')) must stay absolute

## Git / GitHub Actions
- .github/workflows/generate-posts.yml auto-generates data/posts.json
- .github/scripts/generate-posts.js scans blog/posts/*.md and parses YAML frontmatter
  (title, author, date, tags) plus the first prose paragraph as the excerpt
- It exits 1 without writing when no posts are found, so an empty index can never
  be committed by accident (the old version silently produced {"posts": []})
- The workflow also runs `python3 scripts/generate_local_data.py`, so the file:// snapshot
  is committed together with data/posts.json
- Triggers on blog/posts/*.md, blog/posts/*.html, the script, the workflow and
  scripts/generate_local_data.py; workflow_dispatch also works
- Keep memory.txt updated when making structural changes


## Multiplayer lobby (lobby.html)
- Purpose: public room search + peer-to-peer chat. No game server — only room
  discovery touches a backend; chat messages travel directly between browsers.
- Backend: a Cloudflare Worker at https://roomfind.us.ci (custom domain, because
  the default *.workers.dev domain is blocked in mainland China). The Worker uses
  Workers KV to store room entries. Endpoints:
    - POST /announce   {code, name, host}  register a room (TTL 120s)
    - POST /heartbeat  {code}              refresh TTL (host every 20s)
    - GET  /rooms                          list live rooms (last_seen < 90s)
    - POST /leave      {code}              remove a room
- Transport: WebRTC via PeerJS (peerjs@1.5.4, public signalling cloud). The host's
  Peer id = the room code; clients connect straight to the host.
- Room codes: 5 chars from '23456789ABCDEFGHJKMNPQRSTUVWXYZ' (no 0/O/1/I/L).
- Flow: client opens a data connection and sends {type:'join'}; the host validates
  the nickname (rejects duplicates with {type:'reject'}) and answers {type:'welcome'};
  only then does the client enter the room view. Messages are relayed by the host.
- KV is eventually consistent (~13s lag), so the lobby polls /rooms every 10s.
- The Worker source is NOT in this repo — it lives in the Cloudflare dashboard.
  To edit it: Workers & Pages -> square-wave-2fd0 -> Edit code.
- lobby.html is self-contained (inline style + script). It is NOT part of the
  data/*.json pipeline and does not load assets/local-data.js.
